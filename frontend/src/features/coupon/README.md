# 가게별 스탬프 보상 기준 (2026-10-01)

사장님 화면을 만들지 않고, 그 화면에서 저장한 정책을 손님 프론트엔드가 받는 구조를 준비한 버전입니다. 현재는 예시 데이터이며 서버·사장님 화면과 실제 연결되지는 않았습니다.

## 정책 연결 지점

`source.ts`의 `fetchStampPolicies()`를 서버 조회로 교체하세요. 응답은 아래 모양입니다.

```ts
{
  storeId: 'store-005',
  requiredStamps: 8,           // 선물 하나에 필요한 개수. 가게마다 다른 양의 정수
  reward: '아메리카노 1잔',
  unit: '음료 구매',
  condition: '유료 음료 1잔당 1개 적립 · 무료 제공 음료 제외'
}
```

DB의 snake_case 필드 등은 여기서 StampPolicy 타입으로 매핑합니다. 메뉴·보상명·필요 개수를 UI에 따로 하드코딩하지 않습니다. 예시 목표는 가게별 5/6/8/10/12/15개입니다. 과거 10개를 사용한 교환 이력은 과거 정책의 거래로 유지합니다.

## 반영 범위

- 목록과 상세 적립판의 칸 수, 진행률, 남은 개수, 교환 가능 여부.
- 상단에는 **사용 가능한 스탬프 N개**만 표시. 값은 각 가게의 `floor(보유 수 / 필요 수)`를 합산합니다. 검색 필터와 관계없는 전체 보유 선물 수입니다.
- 교환 1회당 해당 가게의 최신 필요 수만 차감합니다. 정책이 낮아져 잔액이 기준을 넘더라도 초과 잔액을 삭제하지 않습니다.
- 30개를 넘는 목표는 개별 도장 대신 수치와 진행 막대로 표시해 화면이 지나치게 길어지지 않습니다.
- 0, 음수, 소수, 잘못된 정책은 노출하지 않습니다. 기본 10개로 대체하지 않습니다.
- 다른 앱 화면이나 브라우저 탭에서 돌아오면 다시 조회합니다. 실시간 구독은 연결하지 않았습니다.
- 시연 적립·교환 직전에 최신 정책과 잔액을 다시 확인합니다. 화면의 규칙과 달라졌으면 작업을 중단하고 갱신을 안내합니다. 중복 클릭도 방지합니다.

## 실제 운영 시 필요한 서버 작업

손님이 보낸 필요 개수·보상명·잔액을 신뢰하면 안 됩니다. 서버에서 가게 권한, 직원 확인, 정책 버전, 실제 잔액, 중복 요청을 검증하고 원자적으로 적립/차감을 처리해야 합니다. 이미 적립 중인 사용자의 정책 변경 적용 시점과 기존 혜택 보호 규칙도 결정해야 합니다. 이 예시는 최신 정책을 재조회하는 방식이며 기존 정책 보장 기능은 아닙니다.

스탬프 잔액과 거래 내역은 Supabase에서 읽습니다. 손님 화면은 잔액을 직접 바꾸지 않습니다. 적립은 손님이 받은 6자리 코드(`issue_stamp_code()`, 3분·1회용)를 사장님이 가게 관리 > 손님 스탬프 찍기에서 입력하면 서버의 `redeem_stamp_code()`가 `apply_stamp_change()`로 처리합니다. 교환은 아직 서버 처리가 필요합니다.

## 수정 범위

frontend 안의 coupon, partner-stores 기능 폴더만 변경했습니다. 학생 제휴의 상단 설명 배너를 제거했고, 기존 검색·단과대 필터·지도·가게 간 연결은 유지했습니다. 사장님 페이지와 공통 컴포넌트, 백엔드는 수정하지 않았습니다.
