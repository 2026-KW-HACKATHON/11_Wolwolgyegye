# 가입·로그인 설계

현재 화면: 일반 사용자는 카카오 간편로그인 또는 이메일·비밀번호 회원가입, 사장님은 이메일·비밀번호 회원가입. DB는 특정 소셜 제공자에 종속되지 않는다.

## 계정을 나누는 기준

| 구분 | 로그인 흐름 | 앱 DB |
|---|---|---|
| 일반 사용자 | 카카오 로그인 또는 이메일 회원가입 → 최초 이용 시 Auth 계정 생성 | profiles 자동 생성, 본인 찜·스탬프 이용 |
| 사장님 신청자 | 이메일 회원가입 → 이메일 인증 → 로그인 → 가게 정보 제출 | profiles + owner_applications(status=pending) |
| 승인된 사장님 | 이메일 로그인 → 본인 가게 관리 | stores.owner_id에 연결된 가게만 수정 |

인증 계정은 둘 다 Supabase `auth.users`를 쓴다. 로그인 제공자 정보는 `auth.identities`가 관리한다. 비밀번호·OAuth 토큰을 앱 테이블에 복사하지 않는다.
소셜 로그인도 첫 이용 시 계정이 생기는 방식이며, 단순 비회원 접속과는 다르다. [소셜 로그인](https://supabase.com/docs/guides/auth/social-login), [이메일·비밀번호 인증](https://supabase.com/docs/guides/auth/passwords)

로그인 방식과 권한은 별개다. 사장님도 주민 기능을 이용할 수 있으므로 `profiles.role`로 양자택일하지 않는다.
**실제 가게 관리 권한은 `stores.owner_id`가 기준**이다. 화면에서는 본인 소유 가게 목록과 본인 신청 상태를 조회해 메뉴를 결정한다. 승인 이력만으로 현재 소유권을 판단하면 안 된다.

## 공통 프로필 생성

`20261004000100_schema.sql`의 사용자 묶음이 Auth 계정 생성 트리거와 기존 계정의 프로필 생성을 맡는다.

- 표시 이름은 display_name → full_name → name → '월계 주민' 순서로 선택하며 최대 40자.
- 기존 프로필/닉네임은 덮어쓰지 않는다.
- 사용자 metadata의 role, is_admin 같은 값으로 권한을 부여하지 않는다.
- 이메일 인증 전에도 프로필은 생성되지만 사장님 신청은 막는다.

Auth 트리거 오류는 회원가입에도 영향을 주므로 실제 Supabase에서 이메일/소셜 가입을 모두 테스트해야 한다. [프로필 트리거 공식 안내](https://supabase.com/docs/guides/auth/managing-user-data)

## 사장님 신청

이메일 인증 완료 후 다음 값을 `owner_applications`에 INSERT한다.

- user_id: 로그인 세션의 사용자 ID
- applicant_name: 신청자 이름
- contact_phone: 심사용 연락처
- store_name: 가게명
- store_address: 가게 주소

인증된 이메일과 email identity가 있어야 신청할 수 있다. 소셜 전용 계정은 바로 사장님 신청이 되지 않는다. 계정 연결/전환 UI는 후속 작업이다.
신청 한 건이 대기 중이면 중복 제출을 막는다. 제출 후 수정/삭제는 허용하지 않으며, 잘못된 정보는 관리자 반려 후 다시 신청한다. 여러 가게를 운영하면 앞선 신청 처리 후 다음 신청을 할 수 있다.

상태는 pending → approved 또는 rejected. 신청자 본인만 내용을 조회하고, 상태·심사 결과·승인 가게 ID를 직접 변경할 수 없다. 민감한 신청 정보는 공개 가게 프로필과 분리된다.
사업자등록번호·증빙 파일은 지금 수집하지 않는다. 검증 정책과 보관 범위를 정한 뒤 전용 비공개 저장소를 추가해야 한다.

## 관리자 처리

서버가 관리자 권한 및 가게 소유 증빙을 먼저 확인한다. 그 후 관리자가 준비한 stores 행을 지정하여 서비스 키로 다음 RPC를 호출한다.

```text
review_owner_application(
  p_application_id: 신청 UUID,
  p_decision: 'approved' 또는 'rejected',
  p_store_id: 승인할 가게 UUID / 반려는 null,
  p_note: 신청자에게 보여 줄 처리 사유
)
```

승인 시 신청 상태 변경과 가게 소유권 연결이 하나의 트랜잭션으로 처리된다. 이미 다른 사람이 소유한 가게는 승인할 수 없다. 동일한 처리 재시도는 안전하게 반환하고, 이미 처리된 결정을 변경하는 호출은 거절한다.
가게 공개(is_published)는 별도로 관리한다. 반려해도 계정/주민 기능은 유지된다. 기존 사장님 권한 회수는 소유권을 별도로 변경해야 하며 과거 신청 기록을 바꾸지 않는다.

관리자 화면·서버 엔드포인트는 아직 없다. RPC는 서비스 키를 가진 서버 전용이고, 프론트 사용자에게 실행 권한이 없다.
서비스 키를 프론트 `VITE_*` 환경변수에 넣지 않는다.

## 실제 연결 때 남은 작업

1. Kakao Developers Client ID/Secret과 OAuth Redirect URL을 Supabase에 설정한다. 2026-10-04 공개 설정 기준 Kakao provider는 비활성화 상태다.
2. 운영 메일 발송용 SMTP와 배포/로컬 Redirect URL을 설정한다. 공개 설정 기준 이메일 가입은 가능하고 이메일 인증이 필요하다.
3. 관리자 검증 후 승인 RPC를 호출할 서버 기능과 관리 화면을 구현한다.
4. 실제 환경에서 카카오 콜백, 이메일 인증·재설정, 사장님 신청·승인, 권한 차단을 확인한다.

카카오맵 JavaScript 키와 카카오 로그인 설정은 다른 설정이다. 지도 키 등록만으로 간편로그인은 활성화되지 않는다.
